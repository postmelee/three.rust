# Task #49 real-content shortlist

Research date: 2026-10-26. This is a source and resource-metadata audit, not a performance result. All sizes below are exact bytes for the named distributed variant; no new model binary, texture payload, or HDRI was downloaded. Littlest Tokyo was already present in the pinned source checkout and its GLB JSON was inspected. No browser, build, profile, or timing run was performed for this research.

## Recommendation

Prepare **Littlest Tokyo first**, then **Bistro Exterior** as a distinct many-mesh content family. Keep **A Beautiful Game** as a moderate-download, dense-geometry interaction case. These are authored public scenes, without added model copies. High CPU cost is a hypothesis to test, not a selection result. None contains morph targets; retain RobotExpressive as the existing morph/skinning correctness reference instead of inventing new morph content.

They are not triangle counts, distinct spatial positions, CPU instruction counts, or observed renderer draw counts. No improvement or CPU-heavy qualification follows from these counts alone.

## Import and acceptance boundaries

Source audit used Editor `mrdoob/three.js@9b4a2ac29c63ccb43fd51c5661f2f873ac2c39b8` and Viewer `donmccurdy/three-gltf-viewer@b5ee5dafe27f953ae1b55f42b5fa3697fef08683`. Editor `editor/js/Loader.js` creates GLTFLoader with DRACO, KTX2 support detection, Meshopt, and a path-aware LoadingManager. Viewer `src/viewer.js` likewise has DRACO/KTX2/Meshopt and maps external asset paths. These establish implementation feasibility, not successful import of these exact scenes. Decoder/transcoder payloads must be pinned, mirrored and included in the resource manifest.

The Viewer original is bundled with Three.js r176, while the candidate comparison pin is r186.1. Preserve the r176 application, build and validate a pure upstream r186 control, then compare matched r186 original/JS/Wasm routes. The current Editor-specific import-map overlay does not replace the Viewer's bundled engine. Viewer decoder URLs also derive from `REVISION`, so a version change must not fetch floating decoder assets.

Before timing, verify resource hashes and absence of network misses; loading and animation names; hierarchy and matrices; native animation phase/progress; skinning where present; correct KTX2/transmission/volume appearance; native selection/focus/orbit/edit behavior; and camera, environment, shadow, quality and resolution parity. Preserve original assets and any failed imports. Record required fallbacks rather than deleting features to reach the prepared path. Keep loading/transcoding, behavioral correctness, diagnostic profiling and uninstrumented timing as separate records.

All selected assets have explicit CC-BY-4.0 evidence. Its [official terms](https://creativecommons.org/licenses/by/4.0/) allow redistribution/adaptation with attribution, license link and modification notices. Retain the supplied copyright and attribution information with any redistributed assets; the repository's code license alone does not cover them. The captured notice manifest lists the precise sources and local archival hashes.
