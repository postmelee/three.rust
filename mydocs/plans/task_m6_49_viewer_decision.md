## Stability screens, fixed before observing primary costs

For each engine scenario let `c` be the largest observed minimum positive clock increment across its pure-r186 baseline runs. The quantization floor is `2*K*c`, hence **8 clock increments** for K=4. This is the existing boundary-based floor, not a measured overhead correction. With `m` the median CPU p50 of all ten original balanced/bookend runs, use `T = max(0.05*m, 8*c)` milliseconds. Every original run p50 must be within T of m, and every 300-group original block p50 within T of its own run p50. Apply the same rule to original-r176 A/B/bookends in the separate migration matrix. Preserve every failing run and block.

Independently screen the four balanced matched-JS repeats in each engine case: compute their own median p50, their own largest observed clock increment and the same 5%/8-increment tolerance; require every JS run p50 and each block-to-own-run p50 delta within that route-specific tolerance. Report the corresponding four-Wasm-repeat screen and all route tails too. These are repeat/block stability diagnostics. **Four JS repeats are not a dedicated JS A/A design and do not replace JS pre/post bookends.** The existing `analysis.aa.passes` field evaluates only the matrix's declared original baseline; it does not implement this additional matched-JS screen or a product adoption verdict.

Compute p50/p95/p99 per run, then the median run quantile for each balanced route; never pool frames as independent repetitions. Report absolute milliseconds, relative changes only above the observed clock floor, ranges, block failures, rAF-timestamp intervals and callback-start intervals separately. An original A/A failure precludes a stable speedup claim and yields an inconclusive performance comparison. A failed JS repeat screen precludes a Rust-specific recommendation. Do not increase samples, warmup, K, tolerances or discard runs after a loss; a justified follow-up needs a new precommitted protocol and output.

## Decisions under adoption-v1

Evaluate every declared animation target independently. Do not average away a target failure or demand a speedup from controls. A low-headroom native target is an acceptable rejection of this candidate/application path; do not replicate content or switch off features to manufacture useful CPU headroom.

1. **Useful path over pure Three.js (G1).** With valid/stable data, both CPU p50 and p95 must improve by at least **20% and 1 ms**, each, over the balanced pure-r186 baseline. For quantile q, this is `baseline[q] - candidate[q] >= max(0.20*baseline[q], 1 ms)`. Apply separately to JS and Wasm. If the candidate misses either basic savings threshold on a declared target, reject adoption of that current path for the declared Viewer target scope. Retain the correct implementation and measurements as experimental evidence if useful; do not promote it as a successful performance replacement. Lack of a sufficiently heavy real workload is a headroom limitation, not permission to lower G1.
2. **Rust-specific effect (G2).** Relative to matched JS, both Wasm CPU p50 and p95 must improve by at least **10% and 0.5 ms**, each: `JS[q] - Wasm[q] >= max(0.10*JS[q], 0.5 ms)`. This must also exceed baseline-specific noise/clock limits. Failing this threshold rejects a Rust-default recommendation for that scope even if the shared design beats Three.js. Passing it in this matrix is only a candidate result: before recommending Rust, precommit and run a dedicated matched-JS A/B and before/after-bookend balanced calibration on the qualifying target cases. Until that additional calibration confirms the effect, the Rust recommendation is **inconclusive**. This conditional work must use fresh captures and preserve the first result; the four JS repeats above are insufficient by themselves.
3. **Controls, tails and cadence (G5).** Preserve the existing policy exactly: "CPU regressions must stay within **max(5%, 0.2 ms)** at p50/p95/p99; p95/p99 frame-interval regressions within **max(5%, 0.2 ms)**, with A/A noise assessed separately." For each metric, use the corresponding baseline quantile in the percentage term. Apply it to small/static and resolution controls and target tails, separately for each candidate versus pure-r186. Also report Wasm-versus-JS tails. Evaluate rAF-timestamp and callback-start interval p95/p99 separately; neither is measured display latency. An observed regression beyond this budget is retained as a rejection of the affected scope when the comparison is stable, rather than hidden by a median win. Noise is assessed separately and is not added to the product regression allowance.
4. **Incomplete or unstable evidence.** Correctness failures reject the affected supported behavior. Invalid captures or failed original A/A make performance inconclusive; their raw costs/regressions remain reportable observations. Missing measurements do not pass. If G1 fails with a valid stable comparison, the current path is rejected even if a profile seems promising. If a path passes this finite CPU screen, describe that narrow result and leave overall adoption unqualified until the remaining gates are actually satisfied.

The existing broader G5 budgets remain **50 ms extra p95 first useful interaction**, **1 MiB extra compressed transfer**, **max(10%, 16 MiB) extra steady/peak application memory**, and 30-minute interaction/acquire-release retained-growth checks. This primary matrix does not measure those. It also does not supply a second asset family, all realistic interaction scenarios, other desktop hardware/browser classes, or repeat sessions on different days required by G1/G6. Larger-content import/profile failures remain part of the evidence and cannot be relabeled as covered primary scenarios. No full product or replacement qualification follows from a finite pass here.

Publish a per-app/per-scenario verdict with exact source hashes, coverage/fallback and actual Wasm counters, primary quantiles/intervals, all stability results, migration costs, failed and unperformed gates. Distinguish shared JS/Wasm architecture effects from a language effect. This matrix tests the current complete path; it does not isolate the causal benefit of the single-node optimization against an older runtime measured under another session.
